# Технічне завдання: веб-додаток CASEVAC для медичного відділу

Версія 0.1 (чернетка) · 26.10.2026

## 1. Загальні відомості

**Робоча назва:** CASEVAC Planner.

**Призначення:** картографічний веб-додаток для медичного відділу організації з гуманітарного розмінування. Додаток дозволяє вести інформаційні картки лікарень, проєктувати та підтримувати в актуальному стані маршрути евакуації (CASEVAC) від мінних полів до лікарень, а також формувати картографічні матеріали (JPG) і План реагування (Word) на кожен маршрут.

**Користувачі:** медики організації. Кожен має персональний акаунт у ArcGIS Enterprise Portal з правом редагування об'єктів.

**Середовище:** ArcGIS Enterprise 11.5; сервіси на gis-services.htgoims.org та gis.htgoims.org; хостинг фінальної версії на GitHub Pages; розробка спочатку локальна. Робота лише онлайн, без сторонніх застосунків.

**Мова інтерфейсу та документів:** українська.

## 2. Мета та межі проєкту

**Мета:** замінити розрізнені ручні процедури єдиним інструментом, де медик виконує весь цикл (картка лікарні → маршрут → карта → План реагування) в одному застосунку.

**Входить в обсяг:**

- вхід через Portal (SSO);
- перегляд веб-карти та шарів;
- створення і редагування карток медичних закладів;
- створення, редагування і деактивація маршрутів евакуації (ручний та автоматичний режими);
- автоматичне створення і супровід початкової точки евакуації та всіх ключів зв'язку;
- експорт карти CASEVAC у JPG (A4/A3, 300 dpi);
- експорт Плану реагування у Word за шаблоном.

**Не входить в обсяг:**

- офлайн-режим;
- історія версій карток лікарень (зберігається лише актуальний стан і дата останнього візиту);
- процес погодження маршрутів;
- розрахунок довжини, часу в дорозі та інших похідних атрибутів маршруту (маршрут є простою полілінією);
- заборонені зони, бар'єри, мережевий аналіз з власними даними;
- редагування шару мінних полів.

## 3. Терміни

- **Мінне поле (завдання)** — об'єкт шару «task Minefield BAC CB», ідентифікується task\_code (унікальний код) і task\_id (унікальний ключ).
- **Маршрут** — лінійний об'єкт шару «Casevac route» від мінного поля до лікарні.
- **Початкова точка евакуації** — точковий об'єкт шару «Start evac point», рівно один на маршрут.
- **Заклад** — об'єкт шару «Medical facilities».
- **Основний / додатковий маршрут** — тип маршруту; для одного поля їх може бути кілька.
- **Актуальний** — маршрут зі статусом «так» станом на сьогодні.

## 4. Архітектура

**4.1 Загальна схема.** Односторінковий клієнтський застосунок (SPA) без власного серверу. Уся логіка виконується в браузері, дані читаються і пишуться напряму в feature services через ArcGIS REST API від імені користувача.

**4.2 Технологічний стек (пропозиція):**

- ArcGIS Maps SDK for JavaScript 4.x (версія, сумісна з Enterprise 11.5, фіксується на старті розробки);
- Calcite Design System для інтерфейсу, локалізація uk;
- TypeScript + Vite; розгортання через GitHub Actions на GitHub Pages;
- бібліотека формування .docx (docx-templates або docxtemplater, остаточний вибір за результатами прототипу).

**4.3 Автентифікація.** OAuth 2.0 (PKCE) до Portal через OAuthInfo та IdentityManager. Client ID: `UkLjSBHNNooE1jnb`. Це публічний ідентифікатор застосунку, не секрет; Client Secret у коді не використовується. Потрібно додати Redirect URI в налаштуваннях застосунку на Portal (адміністратор):

- `http://localhost:5173/` (локальна розробка; порт уточнюється);
- `https://<org>.github.io/<repo>/` (після деплою; адреса буде відома після створення репозиторію).

**4.4 Конфігурація.** Усі адреси (portalUrl, ID веб-карти, URL шарів) зберігаються в одному файлі конфігурації. Жодних даних і токенів у репозиторії.

**4.5 Основа додатку.** Веб-карта `36cc1d881f1145fa8183e1dacc03d88c` завантажується як WebMap; шари знаходяться за URL з конфігурації.

## 6. Модель даних і зв'язки

### 6.1 Ключі зв'язку

| Зв'язок | Ключ |
| --- | --- |
| Мінне поле 1 — N Маршрути | Route.task\_id = Minefield.task\_id (task\_code дублюється для читабельності) |
| Заклад 1 — N Маршрути | Route.med\_facility\_guid = Facility.globalid |
| Маршрут 1 — 1 Початкова точка | StartPoint.parentglobalid = Route.globalid |

Усі ключі заповнюються додатком автоматично; користувач їх не вводить і не бачить як редаговані поля.

### 6.2 Маршрут (Casevac route)

Існуючі поля: task\_id, task\_code, med\_facility\_guid. Необхідно додати (назви уточнюються з адміністратором ГІС):

| Поле | Призначення |
| --- | --- |
| route\_type | тип маршруту: основний / додатковий (домен) |
| is\_current | актуальність: так / ні (домен), за замовчуванням «так» |
| surveyed\_by | ПІБ медика, що обстежив маршрут (вибір зі списку) |
| survey\_date | дата обстеження |

Геометрія — проста полілінія, без Z/M та додаткових розрахунків.

### 6.3 Початкова точка евакуації (Start evac point)

Містить parentglobalid (зв'язок з маршрутом). Рівно одна точка на маршрут. Положення точки — перший вузол полілінії маршруту (початок маршруту біля мінного поля), якщо інше не буде визначено (див. відкриті питання).

### 6.4 Заклад (Medical facilities)

Перелік атрибутів (тип закладу, наявність відділень, обладнання, операції, лікарі тощо) буде наданий окремо та додасться до ТЗ як Додаток А. Додатково до нього обов'язкові: last\_visit\_date (дата останнього візиту) і visited\_by (хто відвідав). Зберігається лише актуальний стан.

### 6.5 Бізнес-правила

1. Для кожного маршруту існує рівно одна початкова точка; вона створюється, переміщується і видаляється разом з маршрутом.
2. Одне поле може мати кілька маршрутів (основний і додаткові); одна лікарня — багато маршрутів.
3. Маршрут не видаляється для виведення з обігу: його статус змінюється на is\_current = «ні». Фізичне видалення — лише як окрема дія з підтвердженням (каскадно видаляє початкову точку).
4. Для поля може бути лише один актуальний основний маршрут: при створенні нового актуального основного додаток пропонує перевести попередній у «неактуальний».
5. Правила 1 і 4 забезпечуються додатком, оскільки сервіс їх не гарантує.

## 7. Функціональні вимоги

### 7.1 Автентифікація та доступ

- **FR-1.** Вхід через OAuth 2.0 до Portal (SSO). Без входу дані та інтерфейс редагування недоступні.
- **FR-2.** У шапці відображаються ім'я користувача та кнопка «Вийти». Токен зберігається лише в сесії браузера.
- **FR-3.** Права визначаються правами акаунта на feature services у Portal. Додаток додаткових ролей не вводить; якщо у користувача немає права редагування, кнопки створення й редагування приховуються.

### 7.2 Карта і навігація

- **FR-4.** Завантаження веб-карти `36cc1d881f1145fa8183e1dacc03d88c`; відображення чотирьох шарів, перемикання видимості, легенда, підкладки з веб-карти.
- **FR-5.** Пошук і вибір мінного поля за task\_code (випадний список із пошуком по введенню) та закладу за назвою.
- **FR-6.** Фільтри: за мінним полем (показати всі його маршрути), за закладом (показати всі маршрути до нього), за актуальністю маршруту, за типом маршруту. Фільтри застосовуються до карти та списку одночасно.
- **FR-7.** Клік по об'єкту відкриває бічну панель із атрибутами та пов'язаними об'єктами (для поля — маршрути й заклади; для закладу — маршрути; для маршруту — поле, заклад, початкова точка).
- **FR-8.** Відображення координат курсора та вибраної точки (формат уточнюється, див. розділ 11).

### 7.3 Картки медичних закладів

- **FR-9.** Перегляд і редагування всіх атрибутів закладу у формі, згрупованій за розділами (загальне, відділення, обладнання, операції, лікарі). Поля з довідниками відображаються списками (домени сервісу).
- **FR-10.** Створення нового закладу: вказання точки на карті, заповнення форми. Обов'язкові поля підсвічуються та перевіряються до збереження.
- **FR-11.** При кожному збереженні змін картки автоматично оновлюються last\_visit\_date (за замовчуванням сьогодні, з можливістю змінити) і visited\_by (вибір зі списку).
- **FR-12.** Відображення дати останнього візиту у списку закладів; позначка «візит давно» для закладів, не відвіданих понад N місяців (N — у конфігурації).
- **FR-13.** Видалення закладів, на які посилаються маршрути, заборонене; потрібне попереднє перенесення чи деактивація маршрутів.

### 7.4 Маршрути евакуації

**Створення (майстер у 4 кроки):**

1. Вибір мінного поля зі списку. Карта наближується до поля, task\_id і task\_code підставляються автоматично.
2. Вибір закладу зі списку (з відображенням відстані по прямій). med\_facility\_guid підставляється автоматично.
3. Вибір режиму: **ручний** або **автоматичний**.
4. Побудова, редагування та збереження маршруту.

- **FR-14 (ручний режим).** Користувач малює полілінію інструментом Sketch від мінного поля до закладу. Підтримується прилипання до вершин існуючих маршрутів і до точок поля та закладу (вмикається/вимикається).
- **FR-15 (автоматичний режим).** Додаток викликає службу маршрутизації між точкою поля та точкою закладу й повертає геометрію маршруту як чернетку на карті. Критерій — найшвидший (з можливістю обрати найкоротший). Заборонені зони та бар'єри не використовуються.
- **FR-16 (редагування чернетки).** Після автоматичної побудови користувач може: (а) переміщувати, додавати та видаляти вершини; (б) додати проміжні точки та перерахувати маршрут (поточна геометрія при цьому замінюється після підтвердження); (в) перемкнутися на ручне перемалювання. Є «Скасувати/Повторити» та «Скинути чернетку».
- **FR-17.** Перед збереженням користувач обирає тип маршруту (основний/додатковий), заповнює surveyed\_by (зі списку) та survey\_date (за замовчуванням сьогодні), підтверджує is\_current.
- **FR-18 (валідація).** Збереження блокується, якщо: не вибрано поле чи заклад; геометрія має менше 2 вершин; не заповнені обов'язкові поля; початок лінії далі від поля, ніж задана відстань (у конфігурації, за замовчуванням 500 м), або кінець далі від закладу, ніж задана відстань. Порушення відображаються підказкою з можливістю переглянути й виправити.
- **FR-19.** Редагування збереженого маршруту: геометрія (вершини), тип, актуальність, ПІБ, дата. Після зміни геометрії початкова точка оновлюється автоматично (див. 7.5).
- **FR-20.** Деактивація маршруту (is\_current = «ні») і повторна активація одним кліком із підтвердженням.
- **FR-21.** Копіювання маршруту як чернетки для створення додаткового на основі існуючого.

### 7.5 Початкова точка евакуації (автоматично)

- **FR-22.** Початкова точка створюється додатком автоматично під час збереження нового маршруту в місці першої вершини полілінії; parentglobalid дорівнює globalid маршруту. Користувач точку вручну не створює.
- **FR-23.** При зміні геометрії маршруту точка переміщується на нову першу вершину. Якщо користувач розгорнув лінію, точка відповідно переміщується.
- **FR-24.** Цілісність: перед збереженням перевіряється, що для маршруту існує не більше однієї точки. При виявленні дубліката або відсутньої точки додаток пропонує виправлення («Відновити точку»). Окремий режим «Перевірка цілісності» показує маршрути без точки та точки без маршруту.
- **FR-25.** Порядок запису: спочатку маршрут (отримання globalid), потім точка. Якщо шар маршрутів і шар точок знаходяться в різних сервісах, транзакція не є атомарною. Додаток при помилці запису другого об'єкта повторює спробу, а потім відкочує перший запис і повідомляє користувача. Якщо сервіс підтримує призначення globalid клієнтом (applyEdits з useGlobalIds), globalid маршруту генерується на клієнті, і обидва записи відправляються одним запитом.

### 7.6 Експорт карти в JPG

- **FR-26.** Експорт карти CASEVAC вибраного маршруту в JPG формату A4 або A3, орієнтація книжкова або альбомна, роздільна здатність 300 dpi (A4 — 2480×3508 px, A3 — 3508×4961 px).
- **FR-27.** Компонування карти формується в додатку (клієнтський рендер): рамка, заголовок, карта (extent автоматично охоплює поле, маршрут і заклад із полями), масштабна лінійка, північна стрілка, легенда, таблиця основних атрибутів маршруту, дата формування. Точний макет надає замовник (окремим описом), змінюється через шаблонну конфігурацію.
- **FR-28.** Перед експортом доступний попередній перегляд і коригування extent та масштабу.
- **FR-29.** Для експорту без втрати тайлів використовується підвантаження підкладки на потрібному рівні; якщо розмір зображення перевищує можливості браузера, додаток повідомляє про це та пропонує A4.

### 7.7 Експорт Плану реагування в Word

- **FR-30.** Генерація .docx за наявним шаблоном замовника. Плейсхолдери, розраховані на SQL, замінюються на плейсхолдери бібліотеки шаблонізації. Відповідність «поле шаблону → джерело даних» оформлюється таблицею (Додаток Б).
- **FR-31.** Джерела полів: мінне поле (task\_\*), маршрут, заклад, початкова точка, вибраний користувач і дата генерації. Карта (JPG, див. 7.6) автоматично вставляється в документ.
- **FR-32.** Файл називається за правилом «CASEVAC\_{task\_code}*{тип}*{дата}.docx». Для маршрутів без заповнених обов'язкових полів експорт блокується з поясненням.
- **FR-33.** Шаблон .docx не зберігається в публічному репозиторії, а завантажується з Portal (елемент типу Document, доступ лише для організації) після входу. Це запобігає публічному доступу до внутрішнього документа.

## 8. Нефункціональні вимоги

- **Продуктивність:** початкове завантаження карти — до 10 с на каналі 10 Мбіт/с; побудова автоматичного маршруту — до 10 с; експорт JPG A3 — до 60 с.
- **Браузери:** актуальні Chrome, Edge, Firefox; Safari — найкраща спроможність. Мінімальна ширина — 1280 px (ПК); адаптивність під планшет — бажана.
- **Мова:** весь інтерфейс, повідомлення про помилки та документи — українською; локалізація стандартних віджетів SDK — uk.
- **Надійність:** при втраті зв'язку чи закінченні сесії не втрачається чернетка маршруту (зберігається в пам'яті сторінки, користувача просять увійти знову). Записи виконуються лише після явної дії «Зберегти».
- **Журналювання:** використовується Editor Tracking сервісів (хто/коли змінив); для цього він має бути ввімкнений на шарах.
- **Підтримка:** код у приватному або публічному репозиторії з README, інструкцією з розгортання і конфігурації.

## 9. Безпека

- У репозиторії відсутні дані, токени, паролі та Client Secret. Відомі публічно: URL сервісів і Client ID.
- Усі запити використовують HTTPS і токен користувача; сервіси не мають бути відкриті анонімно.
- На ArcGIS Server/Portal необхідно додати у CORS-дозволені origin адреси `http://localhost:<port>` і `https://<org>.github.io`, а сервери — у список довірених (Trusted servers) Portal, оскільки шари знаходяться на двох хостах.
- Дані медиків (ПІБ) і координати маршрутів не передаються на сторонні сервіси, крім служби маршрутизації (передаються лише координати початку і кінця).
- Мітки та джерела підкладки погоджуються з політикою безпеки замовника.

## 11. Ризики та відкриті питання

### Ризики

1. **Маршрутизація з Enterprise.** Служба ArcGIS Online (World Route) потребує токена ArcGIS Online і кредитів; користувачі Portal автоматично доступу не мають. Варіанти: налаштувати у Portal службу маршрутизації як utility service з обліковим записом ArcGIS Online, або виконувати запити через проксі. Також якість дорожньої мережі на прифронтових територіях може бути низькою, тому ручне редагування є обов'язковою частиною процесу.
2. **Два хости сервісів.** Токени, CORS і довірені сервери можуть блокувати запити між gis-services.htgoims.org і gis.htgoims.org.
3. **Експорт A3 300 dpi.** Обмеження пам'яті браузера та завантаження тайлів підкладки; потребує раннього прототипу.
4. **Неатомарні записи** у різні сервіси (див. FR-25).
5. **Публічний GitHub Pages.** Код і URL доступні всім; чутливі файли (шаблон Word) зберігаються на Portal.

### Питання до замовника

1. Адреса Portal (portalUrl) і чи доступний він з інтернету.
2. Чи початкова точка евакуації завжди збігається з першою вершиною маршруту, чи це окрема точка (наприклад, пункт збору поблизу поля)?
3. Чи має бути один основний актуальний маршрут на поле (FR-5 і правило 4 у 6.5), і скільки додаткових допустимо?
4. Звідки береться список медиків для вибору (домен поля, окрема таблиця, список у конфігурації) і чи підставляти поточного користувача за замовчуванням?
5. Який формат координат потрібен у картах і Word (десяткові градуси, DMS, MGRS)?
6. Чи можна змінювати схему сервісів (додати поля route\_type, is\_current, surveyed\_by, survey\_date, last\_visit\_date, visited\_by; увімкнути Editor Tracking)?
7. Хто налаштує службу маршрутизації й кредити ArcGIS Online для автоматичного режиму?
8. Чи достатньо відстані прив'язки початку/кінця лінії (500 м) для валідації?
